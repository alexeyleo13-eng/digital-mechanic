# Цифровой механик — описание продукта

Черновик для формы в личном кабинете. Перед отправкой обновите ссылки (репозиторий, стенд, видео) и строки, помеченные `[уточнить]`.

## Назначение

Цифровой механик — AI-агент для механика автопарка. Он работает так:
1. Получает результат акустической проверки двигателя из ML-сервиса НейроДВС.
2. Объясняет, что, вероятно, не так, чем это грозит и что проверить.
3. Отвечает на вопросы строго по заводскому руководству на двигатель выбранной машины, со ссылкой на документ и страницу PDF.
4. По подтверждению механика оформляет заявку на дефектовку в ТОиР.

## Реализовано за время спринта

**Обязательный минимум ТЗ (F1–F7):**
- **Веб-интерфейс с чатом, адаптированный под смартфон.** Механик выбирает ТС из списка с поиском и нажимает кнопку «Получить результат диагностики». Можно выбрать любую проверку из истории.
- **Три исхода проверки обрабатываются по-разному:**
  - «норма» — короткий вердикт;
  - «отклонение» — тип, уверенность, риск, рекомендация, проверки и нормативы по руководству;
  - «сбой проверки» — агент не делает выводов о двигателе и просит повторить запись.
- **Ответы только по руководству на двигатель этого ТС** (модель двигателя берётся из карточки ТС), с указанием документа и страницы PDF. Ссылка в ответе — кнопка, которая открывает текст страницы и PDF на нужном месте. Если данных в руководстве нет, агент так и отвечает и рекомендует дефектовку.
- **Агентная архитектура.** Шесть отдельных инструментов: `get_diagnosis`, `search_manuals`, `read_manual_page`, `get_vehicle_history`, `prepare_ticket`, `submit_ticket`. LLM сама выбирает инструмент по запросу, сценарий не зашит цепочкой if-else.
- **Адреса Mock ML и Mock ТОиР задаются в `.env`.** Провайдер LLM тоже меняется через `.env`.
- **Заявка на дефектовку по контракту ТОиР.** Агент готовит черновик, механик видит весь состав заявки и подтверждает отправку кнопкой. Номер заявки (ticket_id) приложение сохраняет у себя вместе с машиной, проверкой и временем создания.

**Дополнительные задачи:**
- **B1. Память по ТС.** Агент учитывает историю проверок и заявок. Если на эту проверку заявка уже есть, он предупреждает.
- **B2. График anomaly_score** по последним проверкам ТС с оценкой тенденции: рост, снижение или стабильно.
- **B3. Режим «Главный механик».** Сводка по парку (карантин, требует внимания, норма), список ТС по срочности, история проверок и заявок по клику.

**Сверх ТЗ — защита от ошибок:**
- **Проверка чисел в ответе.** Каждое значение с единицей измерения (Н·м, мм, МПа, кгс/см², °C…) автоматически сверяется с текстом страниц, которые агент получил в диалоге. Неподтверждённое значение механик видит с предупреждением.
- **Проверка ссылок.** Ссылка на страницу, которую агент не получал поиском, подсвечивается красным. В заявку такую ссылку сервер не пропустит.
- **Проверка применимости типа неисправности к двигателю.** Например, зажигание у дизеля, ТНВД у бензинового двигателя, узел, которого нет в руководствах на этот двигатель. В таких случаях агент предупреждает о вероятной ошибке классификации и заявку не оформляет. Таких проверок в данных семь.
- **Обоснование приоритета.** Приоритет считается по прозрачному правилу, и механику показано, на чём он основан.
- **Устойчивость к перегрузке LLM.** Агент повторяет запрос и переходит на резервную модель. Без ключа LLM приложение работает в демо-режиме на тех же инструментах.

## Не реализовано

- Голосовой ввод и вывод: по ответу организаторов он не обязателен.
- Распознавание госномера по фото и фото положения стенда (шаги 1–2 описания бизнес-процессов): в ТЗ не обязательны.
- Векторный (семантический) поиск. Используется лексический BM25 со стеммингом; агент переформулирует запрос сам. На контрольных вопросах этого хватило.
- Редактирование заявки в форме. Сейчас изменения просят у агента текстом, он пересобирает черновик.

## Подход и архитектура

```
Браузер (телефон) ──SSE──► FastAPI ──► Агент (цикл LLM + инструменты)
                                         ├─ get_diagnosis ─────────► Mock ML API (URL из .env)
                                         ├─ search_manuals / read_manual_page ─► индекс 6 PDF (BM25, фильтр по двигателю ТС)
                                         ├─ get_vehicle_history ───► vehicles.json + свои заявки
                                         └─ prepare_ticket / submit_ticket ─► Mock ТОиР API (URL из .env)
```

- **Индекс руководств.** PDF разбираются постранично (PyMuPDF). Страницы без текстового слоя (39 шт.) распознаются через Tesseract OCR. Длинные страницы режутся на фрагменты с перекрытием, номер страницы PDF сохраняется.
- **Поиск** выполняется только в руководствах на двигатель выбранного ТС, поэтому норматив от другого двигателя в выдачу попасть не может. Для общих документов (ЯМЗ-236М2/238, ЗМЗ-40904/40905) агенту дана инструкция брать значение для своей модели.
- **Риск и приоритет** считаются детерминированно, LLM их только объясняет:
  - высокий — критичный узел (давление масла, охлаждающая жидкость в масле, цепь ГРМ) или `anomaly_score ≥ 0,80`;
  - средний — важный узел или `anomaly_score ≥ 0,65`;
  - иначе низкий.

  Помехи в записи и низкая уверенность модели выводятся как предупреждение с рекомендацией повторной записи.
- **Системная инструкция агента** задаёт порядок ответа: что видим → вероятные причины → что проверить → возможный ремонт → ограничения. Она также запрещает нормативы «из общих знаний».

## Стек и модели

- **Backend:** Python 3.12, FastAPI, Uvicorn, httpx, Pydantic.
- **LLM:** Google Gemini (AI Studio) через OpenAI-совместимый API. Основная модель `gemini-3.8-flash`, резервные — `gemini-3.7-flash` и `gemini-3.5-flash-lite`. Поддерживаются также Claude (Anthropic SDK) и любой OpenAI-совместимый провайдер.
- **RAG:** PyMuPDF, Tesseract OCR (rus+eng), rank-bm25, snowballstemmer (русский стемминг).
- **Frontend:** HTML, CSS и JS без фреймворков и сборки, SSE-стриминг ответа.
- **Тесты:** pytest — правила агента и проверка чисел.

## Запуск и состав поставки

```
pip install -r requirements.txt
cp .env.example .env      # вписать LLM_API_KEY
python -m scripts.run_all  # заглушки ML (8001), ТОиР (8002) и приложение (8000)
```

Есть Dockerfile. Состав репозитория:
- `app/` — агент, инструменты, сервер, интерфейс;
- `scripts/` — сборка индекса, загрузка PDF, запуск, проверка LLM, контрольный прогон;
- `data/index/` — готовый индекс;
- `mock_services/` — заглушки заказчика;
- `tests/`.
